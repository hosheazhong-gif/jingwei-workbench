# 24. 多类型工作台讨论稿

**状态：讨论稿，不是 PRD，不是裁定。** 按第 14 节扩展准入规则，这份稿只用于讨论；讨论出结论后再决定写不写进 PRD，写进 PRD 之后才动代码。本轮没有新建模板、没有改 `domain/`、没有写一行实现代码。

**由来**：2026-08-23，产品所有者在 PRD 第 20.2 节收口之后提出——最终目标是**咨询行业的多类型工作台**；设想是「既然咨询相同，是不是可以拆分成几个模块，完全体的产品可以选择自己需要的模块进入工作台」，举的例子是**搜索、文档润色、产业图谱、公司 AI 应用化**；并要求先了解其他咨询业务类型实际在做什么，以及去 GitHub 上看有没有已经做得比较完善的同类项目，再判断可行性。产品所有者明确只熟悉**地产咨询**，不了解 technology consultant 和其他类型顾问的工作。

**这份稿回答四个问题**：别的咨询到底在干什么；共同骨架是什么、不同的那一段在哪；有没有人已经把经纬要做的事做完了；「拆成可选模块」这个设想立不立得住、该怎么落。

**调研口径与不确定性**：本稿的事实部分来自 2026-08-23 的公开检索，来源清单在第 6 节。开源项目的 star 数和最近活跃时间是当日实查，会过时。凡是没有查到可靠来源的地方，正文里写明「推断」。有三处硬性缺口先说在前面：(1) 各类咨询里「公开材料 / 客户材料 / 访谈」各占多少，**任何一类都没有查到可信的量化数据**；(2) 中文语境下组织人力咨询的实际周节奏没有可信公开来源；(3) 数字化转型咨询搜到的几乎全是服务商营销页。这三处的相关判断都是推断。

## 1. 别的咨询实际在干什么

调研了六类：战略/管理咨询、技术咨询、尽职调查（商业尽调 CDD / 技术尽调 TDD）、产业规划与产业图谱、市场研究与竞争情报、组织与人力咨询。这里只留对经纬有判断价值的部分。

### 1.1 材料从哪来，差别比想象的大得多

这是六类之间**最大的分野**，也是直接决定经纬能不能装得下的那一条。

| 类型 | 主要入口 | 公开网页占比（推断） |
|---|---|---|
| 竞争情报 | 竞对官网、财报、新闻 + 内部销售一手情报 | 最高 |
| 产业规划 | 政策文件 + 统计数据 + 企业数据库 | 高 |
| 战略咨询（外部题型） | 二手报告 + 专家访谈 + 客户数据 | 中 |
| 市场研究 | 自采一手数据（问卷、深访），二手只做基线 | 低 |
| 商业尽调 | 数据室文件 + 客户访谈 + 问卷 + 专家电话 | 低 |
| 技术咨询 | 客户内部现状 + 一线用户访谈 + 供应商回复 | 很低 |
| 技术尽调 | 代码仓库 + 扫描结果 + 工程师访谈 | 接近零 |
| 组织人力 | 花名册、编制表、薪酬表 + 访谈 + 付费薪酬调研库 | 最低 |

**经纬现在只有一个入口：公开网页。** 表里越靠上的越装得进，越靠下的越装不进——**不是功能不够，是原料不在网上。**

### 1.2 几个具体的样子（帮助理解「顾问那一周在干什么」）

- **战略咨询**：8–12 周、2–6 人。第 1–2 周先做 **ghost deck**——大约两成完成度的 PPT，每页只有标题和图表草图，正文空着；这份骨架一经审过就直接回答「故事线要不要改／缺什么／怎么去拿」。之后在「改故事线」和「跑数做页子」之间来回切。一个项目产出几百页 slide 不罕见，单份 deck 迭代 **40 版以上是常态**。
- **技术咨询（ERP 选型）**：全程 6–9 个月。访谈 **15–30 名一线业务人员**出问题清单，然后写 **60–200 页需求文档**，再把需求文档机械地转成 RFP 问卷和加权评分矩阵。压缩到 4 个月以内「会在上线后 18 个月内可靠地产生买家后悔」。
- **商业尽调**：4–8 周。**第 1 周就把投资逻辑拆成 3–5 条可检验命题**，做成 2–3 页清单，每条标 must-have / nice-to-have。然后是一个 **2–3 周的收集冲刺**：15–30 场客户访谈、100–200 份问卷、6–12 家直接竞对、5–10 场专家电话。全程每周维护一页「so what」，记本周发现和未决问题。
- **产业规划**：交付物不是「一份稿」，**是一条稿件版本流水线**——初稿 / 讨论稿 / 征求意见稿 / 审议稿。每一版之间的差异来自「某个部门提了意见」，不是「又查到了新材料」。产业图谱的绘制是 7 步，最费力的是**企业名录的采集、清洗、判断属于产业链哪个环节、分层**。
- **组织人力**：核心产出是**编制表和薪酬测算**这类算出来的东西；访谈证据**必须匿名化聚合**（不能写「CFO 说销售部人浮于事」）——这跟「把原话挂到问题上」方向相反。

### 1.3 共同骨架：九步，经纬现在踩住了其中几步

把六类的做法对齐之后，共同骨架是九个动词。经纬现在的循环覆盖其中一段：

| # | 动词 | 经纬现状 |
|---|---|---|
| 1 | 界定问题 | **有**（经理一句话） |
| 2 | **搭结论骨架** | **半有**。经纬拆的是**问题**；行业里通行的做法是先定「稿子长什么样」，再倒推要查什么（ghost deck、CDD 的 3–5 条命题清单、需求文档目录、规划大纲） |
| 3 | 找材料 | **有**（仅公开网页） |
| 4 | 从材料提取事实 | **半有**。经纬挂的是**原话**；六类里有五类的中间产物是**表**（企业清单、需求条目、评分矩阵、交叉表、编制表） |
| 5 | **算** | **完全没有**。财务模型、加权评分、交叉表、定编测算 |
| 6 | 形成判断 | 半有（模型写候选） |
| 7 | 组织成交付物 | **有**（仅成稿。行业里还有图、表、制度文件、系统） |
| 8 | 复核 | 半有（人点「收下」）。尽调的复核是独立步骤且有法律后果；产业规划的复核是专家论证会 + 多部门征求意见 |
| 9 | **迭代版本** | **完全没有**。「这一版跟上一版差在哪、哪条意见导致的」 |

**第 2 步值得单独提。** 经纬现在是「拆成本轮几条研究问题 → 去搜」。行业里成熟做法是**先立骨架再找料**：骨架同时回答「这条问题的答案将来落在稿子的哪一节、以什么形状呈现」。如果经纬的拆问题这一步能顺手输出「这条问题对应稿的哪一节」，就跟行业实践对上了，而且成本很低——**这可能是本稿里性价比最高的一条建议。**

**第 5 步和第 9 步是真正的缺口，且第 9 步更要命。** 战略咨询 deck 迭代 40 版、产业规划强制经过四轮评审、竞争情报要把新事实同步到已发布的卡片——**三类活的实际痛点都是「改」，不是「写」。** 经纬的「人点收下才进稿」解决了第一次进稿的质量；`material_since_draft`（一节收下后又挂了几条原话）算是往第 9 步走了半步，但还回答不了「我改了这一节，别的节受不受影响」。

### 1.4 哪几类根本装不进现在这条循环

**完全装不进（四类）：**

1. **技术尽调**。证据是代码仓库、扫描结果、许可证清单，不存在「网页原话」这个对象；结论是 30 项打分算出来的。
2. **组织与人力咨询**。三重不兼容：材料在客户内部；核心产出是计算结果；访谈证据必须匿名化聚合，与「挂原话」方向相反。
3. **市场研究的定量部分**。开放题编码看着像「挂原话」，实则是**降维**——要的不是这句话本身，是「持这类观点的人占 34%」。
4. **竞争情报**。不是「一轮出一份稿」，是常年循环 + 一堆持续维护的短卡片；痛点是一条新事实要同步更新 N 张已发布的 battlecard，是「知识库 + 变更传播」的形状。

**装得进一半（四类）：**

5. **商业尽调**——案头段（行业、竞对、公开数据）完全装得进，而且**它对「每条结论挂证据」的刚性需求正好是经纬的强项**（尽调报告要出具依赖函，有法律责任）。装不进的是访谈和问卷的执行与归并，而证据主体恰恰在那里。
6. **产业规划**——「为什么」那一层（政策解读、背景、对标案例）装得进，政策原文引用正是经纬的形状。装不进：企业名录的采集清洗分层、图的绘制、以及多轮评审驱动的版本流。
7. **战略咨询**——外部事实基础那一段完全装得进，ghost deck 的逻辑和经纬高度同构。财务模型那一段装不进。
8. **技术咨询**——技术趋势/供应商图景那一段装得进；主体（需求收集、现状梳理、评分矩阵）装不进。

**扩张的最短路径按契合度排序：商业尽调的案头段 > 产业规划的背景与对标段 > 战略咨询的事实基础段 > 竞争情报的定期深挖。** 这四个都不需要改变产品的基本形状。

## 2. GitHub 上有没有人做完了

结论先说：**没有，而且不是「差一点」，是三个项目各占一个角、中间没人。**

调研范围：GitHub `deep-research` topic 下 566 个仓库，逐个核实了头部项目；另核实了 Dify / n8n / Flowise / RAGFlow / AnythingLLM / Khoj / Onyx / Logseq / Obsidian 这一批可组合平台。**注意：没有穷尽 566 个仓库**，下面「没人做」的判断是基于头部核实的推断，不是穷举证明。

### 2.1 同类项目的实际状态（2026-08-23 实查）

| 项目 | stars | 最后推送 | 人在环的位置 | 存不存原文 | 逐句可溯 |
|---|---|---|---|---|---|
| bytedance/deer-flow | ~80k | 极活跃 | **「计划」层的阻塞门** | 有渲染捕获 | 否 |
| stanford-oval/storm | 31.1k | **2025-09-30（停滞 11 个月）** | Co-STORM 在「收集对话」层 | 存 snippet | 部分（节级） |
| assafelovic/gpt-researcher | 29.1k | 2026-07-18 | 可选反馈 | **否（存摘要）** | 否 |
| dzhng/deep-research | 19.6k | 2026-04-11 | 无 | 否 | 否 |

### 2.2 本次调研最重要的一条发现

> **开源界普遍有「人在环」，但所有项目的门都在「计划／大纲」这一层，没有一个在「单条证据」这一层。**

DeerFlow（8 万 star，字节在投）做了真正的阻塞门：计划生成后必须人点 `[ACCEPTED]` 才继续，也可以用自然语言说 `[EDIT PLAN] 补充技术实现相关步骤`。LangChain 的 open_deep_research 也做过计划审批——**然后把那一版降级成了 legacy，主线转向全自动。**

原因不难理解：**门放在计划层，人点一次就能跑完，产品体验好；门放在证据层，人要点几十次，体验「差」。**

**而经纬是故意选了那个体验更差的位置。** 这不是技术优势，是责任选择——开源项目的用户不承担交付责任，咨询顾问承担。**这是经纬唯一一条我认为立得住的差异点。**

### 2.3 经纬循环的十二个环节，七个有现成的，五个是空白

| 经纬的环节 | 最接近的现成实现 | 判断 |
|---|---|---|
| 一句话 → 拆研究问题 | STORM 的多视角提问 / DeerFlow 的 planner | 可直接抄 |
| 计划要人确认 | **DeerFlow 的 `[ACCEPTED]` / `[EDIT PLAN]` 协议** | 可直接抄，成本极低 |
| 按问题搜网页 | gpt-researcher 的 retriever 契约（只要 `url` + `raw_content` 两个字段） | 可直接抄 |
| 存网页快照 | **ArchiveBox**（28.1k star，MIT，SQLite + 普通文件夹，栈和经纬同构） | **不要自己造** |
| 从快照逐字扒原话挂到问题上 | 无 | **空白** |
| 模型只按已挂原话写候选 | 无（Anthropic Citations API 提供了机制，但没人这么用） | **空白** |
| 人点「收下」才进稿 | due-diligence-agents 的阻塞闸门（流程级，非证据级） | **空白** |
| 证据归属分三档 | 无 | **空白** |
| 轮次机制 | 无 | **空白** |
| 经理版 + 详细版同源 | **due-diligence-agents 的四层渐进披露 HTML**（决策→行动→细节→证据） | 现成，且比导两份文件更好 |
| 导出 Word | gpt-researcher 的 `publish_formats` | 可直接抄 |
| 对象不删只归档 | 常规软件工程 | 无差距 |

**五个空白全部集中在「证据如何被人控制着进入稿件」这一段。这就是经纬的全部价值所在。**

### 2.4 咨询垂直是空地

`due-diligence` 这个 topic 下绝大部分是合规筛查、制裁名单核查，不是研究报告生成。真正对口的只有两个：一个 56 star（做得最扎实，但只读数据室文档不搜网），一个 2.2k star（搜网但证据处理很弱）。**通用 deep research 挤满了（566 个仓库，头部 8 万 star），垂直咨询是真空。**

空地通常有空地的原因。**推断**有三种可能：(a) 咨询行业不用开源工具，用 Excel + Word + 人；(b) 已被闭源商业产品占据；(c) 每家的方法论都不一样，做不出通用件。**倾向 (a)+(c) 是主因——这意味着经纬的正确定位可能是「自用/小范围工具」，不是「开源项目」。**

### 2.5 别自己造的清单

| 环节 | 用什么 |
|---|---|
| 网页快照 | **ArchiveBox**（MIT，存原始 HTML + singlefile + 截图 + PDF + WARC，存储就是文件夹 + SQLite） |
| 快照的第二重保险 | Wayback 存档 URL（抄 local-deep-research 的做法）。受控副本有「你说这是原文、客户凭什么信」的问题，挂个第三方存档很便宜 |
| 逐字引用 + 字符偏移 | **Anthropic Citations API 的 custom content 模式**——自己按快照段落切块，`cited_text` 由 API 从原文抽取而非模型生成，偏移量能对回自己的快照。注意它**不能和 structured outputs 同时用** |
| 数字溯源 | **due-diligence-agents 的 `numerical_manifest.json`**：单独一张表存稿件里出现的每一个数字及其来源。**模型编数字比编论述隐蔽得多**，这是最便宜的高价值不变量 |
| 自测引用质量 | Ragas 的 faithfulness（15.4k star，活跃）；口径按 ALCE 的 citation precision / recall |
| 出稿闸门 | Vectara HHEM（可本地跑的幻觉检测小模型） |
| 抽查「模型是不是真按材料写的」 | ContextCite（334 star，MIT，靠删掉上下文看输出变不变来做反向归因） |
| 死链 / 编造链接检测 | urlhealth（论文配套开源工具） |

补一条外部数据，说明这件事有多真：一篇 2026 年的实测论文发现，**3–13% 的引用 URL 是模型编的，5–18% 整体不可解析；deep research agent 比普通搜索增强 LLM 更糟（10.7% vs 4.8%）**；更早的研究发现生成式搜索引擎里**只有 51.5% 的句子被其所附引用完全支持**。这正是「引用指向一个会变、会死、会被改的东西」的必然结果——**经纬把引用锚在自己冻结的快照上，方向是对的。**

## 3. 「拆成可选模块」这个设想，我的意见

**先说立场：设想的方向对，但「模块」这个词现在指了四种不同的东西；如果不先拆开，做出来会是四不像。** 而且有一条更要紧的风险在第 3.4 节。

### 3.1 你举的四个例子，其实是四种东西

| 你说的 | 它实际是什么 | 该落在哪 | 难度 |
|---|---|---|---|
| **搜索** | 一个数据源 | `WebSearchAdapter` / `SourceAdapter` | **低**。窄接口，多个开源参考实现 |
| **文档润色** | 对已有稿件的局部变换 | **不该是模块，该是稿上的块级操作**（选中一段 → 润色／缩写／扩写） | **低**。DeerFlow 的 Notion 式块编辑器已经证明了正确形态 |
| **产业图谱** | 一个新的数据模型（实体、关系、图） | **哪个接缝都不是。这是第二个产品** | **高** |
| **公司 AI 应用化** | 一套方法论：问题清单 + 章节结构 + 归属规则 | `ProjectTemplate`（**配置，不是代码**） | **低。根本不用写代码** |

**建议把「模块」明确劈成两层，以后各说各的，不要再混着谈：**

- **能力接缝（代码级，要少、要窄）**：`SourceAdapter` / `WebSearchAdapter` / `Parser` / `DeliverableExporter` / `ViewProjection`。就这五个。
- **方法论模板（配置级，可以多、可以杂）**：`ProjectTemplate` = 一套预设的研究问题清单 + 章节结构 + 证据归属规则，用 JSON/YAML 描述。**「公司 AI 应用化」「行业进入分析」「竞品调研」这类咨询模块，九成九应该落在这一层。**

### 3.2 接口窄的模块活，接口宽的模块死——这条有硬数据

这是本次调研里最可靠的一条规律，证据不是道理，是实测：

- **n8n**（20.2 万 star，195 个官方节点）：对 6000+ 个真实工作流的抓取分析显示，**73% 的工作流用 HTTP Request 节点，52% 用 Code 节点，40% 的工作流只有 5 个以内的节点，中位数 8.5 个。** 另一份按 7800 个公开模板加权的统计里，部署量第一名是**便签**（不是功能节点），第 1 名到第 9 名跌 14 倍。
  > 翻译成人话：**在一个有 195 个官方模块、上千个社区模块的成熟平台上，一半以上的用户最后是靠「发个 HTTP 请求 + 写段代码」这两个万能兜底件把事情做完的，而且只拼 5–8 个件。**
- **Obsidian**：6938 个社区插件。官方自己在博客里承认审核跟不上、首次通过之后的版本根本没被复审。而所有「必装插件」清单反复推荐的是同样那二三十个。**插件数量不是资产，是负债。**
- **Flowise**：fork/star 比 0.46，远高于同类（Dify 0.16、n8n 0.30、RAGFlow 0.12）。**推断**是大量人 fork 去改代码自用而不是直接用官方版——这对「可视化编排能替代写代码」是负面证据（也可能只是教学场景导致的）。

对照经纬预留的九个接缝：

| 接缝 | 接口 | 开源实证 | 建议 |
|---|---|---|---|
| `WebSearchAdapter` | 极窄（query → `{url, raw_content}`） | gpt-researcher / Onyx connector / local-deep-research 十几个源，**全部成功** | **保留，照抄两字段契约** |
| `SourceAdapter` | 窄 | 同上 | **保留** |
| `Parser` | 窄（字节流 → 结构化块） | RAGFlow 的核心卖点 | **保留** |
| `DeliverableExporter` | 窄（数据 → 文件） | gpt-researcher 的 `publish_formats` | **保留** |
| `ViewProjection` | 窄（同一份数据 → 不同视图） | due-diligence-agents 的四层披露 | **保留** |
| `ProjectTemplate` | 中（配置不是代码） | company-research-agent 的四维度分法可当第一个模板 | **保留，当配置** |
| `AnalysisArtifact` | 宽 | 无明确实证 | **推迟** |
| `AnalysisModule` | 宽 | Dify plugin / Obsidian 插件的长尾荒漠 | **推迟到有第二个真实模块再定形** |
| `ExecutionStrategy` | 极宽 | n8n 的 52% 要写 Code——这种抽象一定会漏 | **建议删掉，或退化成「一个能塞 Python 的口子」** |

### 3.3 更扎心的一条：预留接缝本身，价值是零

**STORM 是最好的反面教材。** 它 v0.1.0 的 release notes 标题就叫 "code refactoring and modularity improvements"，很早就把 Retrieval / Question Asking / Article Generation 拆成了干净的可替换接口。结果：**31.1k star，2025-09-30 之后 11 个月没有推送，最后一个 release 停在 2025-01-23。干净的模块化并没有换来任何人接手维护。**

反过来看活着的：Onyx 从「公司内部搜索」一件事起步，做透了才铺 connector；RAGFlow 从「文档解析」一件事起步；**Dify 是到 v1.0.0 才开始做 plugin 生态——在那之前它已经是十万 star 的产品了。插件是结果，不是原因。**

**所以：经纬预留九个接缝这件事，到今天为止产生的价值是零。接缝的价值只在你真的往里插进第二个实现的那一刻才兑现，在那之前它只是让代码更难改。** 这不是说预留错了——docs/19 当时的判断是对的——而是说**别再往接缝上投入了，去插第二个实现。**

还有一条前提问题：**经纬是单机、单用户、无云端的工具，它连「社区」这个前提都不具备。** 没有第三方开发者，所有模块都得自己写。所以「模块市场」这个形态在经纬上根本不成立，规划时应该按「自己写 3–5 个、用户装 1–2 个」来算。

### 3.4 最要紧的风险：多类型会威胁到你唯一的真差异点

经纬现在有两条我认为立得住的东西：**证据层的收下门**，和**证据归属分三档**（客户提供 / 经理反馈 / 公开材料，不许混）。

第二条是纯领域规则，开源界不会长出来——**但它是地产咨询和尽调语境的产物。** 换个题型就未必成立：

- **组织人力咨询**要求访谈证据**匿名化聚合**，方向与「把原话挂到问题上」相反。
- **市场研究**的定量部分要的是「持这类观点的人占 34%」，是降维，不是原话。
- **技术咨询**追溯的是「需求条目 ↔ 供应商回答」的双向可追溯，不是「结论 ↔ 网页原话」。

**如果为了「多类型」把这三种都硬塞进来，最可能的结果不是产品变强，是三档归属规则被磨软成「来源」两个字，然后经纬就变成又一个 deep research 工具——而那个赛道有八万 star 的对手和字节在投。**

所以我的建议是：**多类型的扩张必须限定在「不动那两条不变量」的范围内。** 第 1.4 节那个排序（商业尽调案头段 > 产业规划背景段 > 战略咨询事实基础段 > 竞争情报定期深挖）就是按这个标准排的——这四个都是「以公开材料为主、以文本为交付物、且需要证据追溯」的活，装进来不用改形状。

## 4. 如果要动，建议的下一刀

**不要做模块系统。做第二个 `ProjectTemplate`，纯配置，一行实现代码都不写。**

理由：这是检验「同一条循环换个题型还成不成立」最便宜的办法。**如果连一个模板都撑不住，模块系统更撑不住；如果一个模板撑住了，第二第三个模板的边际成本接近零，那时再谈要不要做模块系统也不迟。**

具体建议：

1. **选一个题型做第二个模板。** 我推荐**商业尽调的案头段**（行业格局、竞对画像、公开财务与新闻），因为它对「每条结论挂证据」的刚性需求正好是经纬的强项，而且它的骨架是现成的（投资逻辑拆成 3–5 条可检验命题、每条标 must-have / nice-to-have）。次选是产业规划的背景与对标段——那个更贴近产品所有者已有的地产/园区经验，风险更低但验证价值也更低。
2. **模板里只放三样东西**：预设的研究问题清单（或问题框架）、稿的章节结构、证据归属规则。**不许放代码。** 如果发现某个模板必须写代码才能表达，那件事本身就是一个要单独讨论的信号。
3. **顺手做两件极便宜、极高价值的事**（都不属于多类型，属于把现有循环做扎实）：
   - **拆问题时同时输出「这条问题的答案落在稿的哪一节」**——把第 2 步的「先立骨架再找料」补上，跟行业通行做法对齐。
   - **数字清单**（抄 `numerical_manifest.json`）：稿里出现的每个数字单独建表挂来源，做成可自动校验的不变量。模型编数字比编论述隐蔽得多，这是当前最容易被违反的一条硬规则。
4. **明确不碰的**：通用 deep research 的能力军备竞赛（那块结束了）；可视化工作流编排；插件市场；`ExecutionStrategy` 这个接缝；产业图谱（它是第二个产品，塞进当前循环会同时破坏循环的简洁和它自己的表达能力）。
