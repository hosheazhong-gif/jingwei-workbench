# 26. 检索代理 A/B 对照 · 第一轮结论

> 日期：2026-08-30
> 对照对象：固定 Workflow（`search_materials`）vs 单一研究 Agent（`agent_search_materials`）
> 题目：P-002 / RQ-011「周边及可比区域有哪些冷链/高标仓园区项目？」
> 原始记录：[25_AB原始记录.md](25_AB原始记录.md)（**会被下次运行覆盖，重跑请加轮次后缀**）
> 依据：[11_Multi-Agent可行性验证方案.md](11_Multi-Agent可行性验证方案.md)

## 1. 结论

**本轮无效，不采用 Agent。**

按 §11.6 的采用规则，本轮既不能证明代理更好，也不能证明它更差——因为
**两组跑的根本不是同一个实验**，而且真正的约束在别处。但这一轮不是白跑：
它测出了一个比原问题更靠前的瓶颈。

**更进一步的判断（见第 4 节）：代理的上线被一个产品前提阻塞，而不是被实验结论阻塞。**
在搜索源成为用户可配置的一等公民之前，测不测都不该上。

| 判定 | |
|---|---|
| Agent 明显更好 → 上线 | ✗ |
| 打平 → 不上线 | ✗ |
| Agent 更差 → 不上线 | ✗ |
| **本轮无效 → 记下缺陷，改了重跑** | **✓** |

## 3. 三条发现

### 3.1 真正的瓶颈是检索后端，不是执行策略

代理一共换出 3 条新检索词，其中 **2 条被公开搜索拦截**，观测原文：

> 「杭州萧山 冷链园区 租金 每平方米」检索失败：公开搜索被拦截。
> 「深圳盐田 冷链仓库 租金 万纬有信达」检索失败：公开搜索被拦截。

第 2 轮整轮颗粒无收。真正拿到结果的换词只有第 3 轮的一条。

**在换成有配额的搜索 API 之前，做多轮代理是浪费。** 任何策略都赢不过一个
每次只回 4 条、还随时被拦的后端——多跑几轮只是多撞几次墙。这一条改变了
优先级：`WebSearchAdapter` 的稳定性排在 `ExecutionStrategy` 之前。

### 3.2 固定流程的提前退出让对照不成立

`search_materials` 的查询循环末尾原本是：

```python
        if added:
            break
```

**第一条检索词只要出结果，后面几条就不搜了。**

证据：两组第 1 轮用的是同样 3 条种子词，A 出 4 条候选（一条词的量），
B 出 12 条（三条词都跑了）。第 1 轮那 8 条差距**与代理无关**，
纯粹是"跑了几条词"的差别。

这是本轮设计的第三个缺陷（前两个是候选上限过低、两组未共用种子词，
已在上一轮修掉）。修法：加 `STOP_AFTER_FIRST_PRODUCTIVE_QUERY` 开关，
线上默认行为不变，A/B 时由 `scripts/ab_search.py` 临时关掉并还原。

### 3.3 代理的换词判断是对的，但换出来的材料有一类正好踩坑

代理第 2 轮的思考：

> 已有候选多为通用租金与仓库类型资料，缺少具体可比园区项目及租金数据，
> 需按地域和项目名细化搜索

随后从泛化口径切到**地域 + 具体运营商名**（杭州萧山、深圳盐田、万纬、有信达）。
这是顾问会做的动作，固定流程做不到——它把三条问题原文（连问号一起）
当检索词发出去，一次成型，不会因为结果太泛而回头调整。

**但"多找到"不等于"找得更好"。** 代理多出的 14 条里有一类是仓库中介平台
（`99cfw.com`、`cangxiaoer.com`、`gys.cn`）。这些页面上确有租金数字、也扒得出，
但那是**挂牌价、渠道商口径**——正是 README「挑材料最容易踩的三样」的第一条：

> 渠道商的 SEO 页常排在官方前面，页上真有价格和参数、也真能逐字扒。
> 挂上去就是把渠道话术当成了官方定价。

**代理越能干，越需要证据层的闸门。** 它扩大的是候选面，不是可信度；
把关那一步仍然只能是人。这反过来支持了产品的基本判断——
门放在单条证据上，而不是放在计划层。

## 4. 真正的阻塞是产品前提，不是实验结论

第 3.1 节说「`WebSearchAdapter` 的稳定性排在 `ExecutionStrategy` 之前」。
把这句话说到底，它不是优先级排序，是**前置条件**：

```
能扛住多轮请求的搜索源  ←── 必须先有
        ↓
    多轮代理才有意义
        ↓
    才谈得上 A/B 与上线
```

经纬默认的搜索源是免费抓页面。它单次搜一下没问题，**连着发六次就被拦**——
本轮第 2 轮两条检索词全军覆没就是证据。而代理的全部价值就是多轮：
**它要的东西，恰好是默认搜索源给不了的。**

### 4.1 就算 A/B 跑赢了也不能上

假设配好带配额的搜索 API、第三轮跑出代理明显更好。然后呢？

用户下载 exe、双击运行、**不需要账号也不需要 API Key**——这是 README 里
写死的承诺。他们用的是那个会被拦的免费搜索源。给这些用户开代理，
结果是更慢、更贵、撞墙撞得更快。

**所以代理真正的上线条件不是「A/B 跑赢」，是「用户有一个能扛住多轮的搜索源」。
那是一个产品功能，不是一个实验结论。**

### 4.2 上线前要做的三件事

1. **把搜索源做成用户可配的一等公民**——像「连接模型」那样，
   界面上有「连接搜索」：选服务、填 Key、保存并测试。模式现成，照抄即可。
2. **代理只在检测到带 Key 的搜索源时可用**；默认免费源下置灰，
   并说明原因（"多轮检索会被公开搜索拦截，请先连接搜索服务"）。
3. **然后**才是 A/B、才是上线判断。

三步做完，代理是不是真有用仍是开放问题——但那时候问这个问题才有意义。

### 4.3 顺带澄清一个不成立的替代方案

排障中考虑过用「录制/回放」的搜索适配器绕开被拦截。**它解决不了这件事。**

回放能让改 A/B 设计不烧配额（上限、种子传递、transcript 完整性都可离线验），
但**评估不了换词的价值**——换词的价值恰恰在于搜了没搜过的词，
而回放里只有录过的 query。它是测试脚手架，不是搜索源的替代品。

## 5. 下一轮的前置条件

三条都满足才重跑，缺一条数据仍然不可用：

1. **配好有配额的搜索 API**（`JINGWEI_SEARCH_PROVIDER=brave` + `JINGWEI_SEARCH_API_KEY`），
   消除被拦截这个混淆变量；
2. **A 组跑完全部种子词**（`--a-runs-all-queries`，现已是对照默认）；
3. **候选上限设到两组都不会顶格**，否则轮数与换词表现被上限压住。

原始记录保留轮次后缀，不要互相覆盖：`--out docs/25_AB原始记录_R3.md`。

**但按第 4 节的判断，第三轮的优先级低于 4.2 那三件事。**
先把搜索源做成可配置的，代理的问题会自己变清楚。

## 6. 已连带修掉的三处"两地各写一遍"

本轮排障中暴露的同类缺陷，与 [20 §6](20_P0纵向闭环实施记录.md) 里
「手写清单一定会漂移，除非有测试盯着」是同一个病：

| 现象 | 根因 |
|---|---|
| CLI 建题目报「未找到模板 industry_chain」 | 模板文件夹名与 `template_key` 不一致，且 CLI 没有查询入口 |
| `scripts/ab_search.py` 读不到 API Key | `cli.py` 调了 `load_local_env`，新脚本没调 |
| `import app` 失败 | 新脚本漏了 `run_test_shard.py` 那套 `sys.path` 引导 |

**已做**（2026-08-30）：

- `app/cli.py` 新增 `list-templates`，印出 key／名称／验到什么程度，
  命令行用户不必再猜目录名；
- `tests/test_script_entrypoints.py` 把这几条写成不变量：引了 `app` 的脚本
  必须做 `sys.path` 引导、要用密钥的脚本必须调 `load_local_env`、
  CLI 必须留有查模板 key 的入口、默认模板 key 必须真的存在；
- 四条现场缺陷已进 [20 §6](20_P0纵向闭环实施记录.md)（123 → 127 条）。

这是本表第三次出现「同一件事在两处各写一遍，第二处忘了同步」。
前两次是 README 的模板名、`serve` 的路由横幅。**同型缺陷第三次出现，
说明该补的不是这一处，是这一类**——所以这次补的是入口不变量，不是单个 bug。
