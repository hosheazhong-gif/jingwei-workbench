# PRD v0.3｜经纬：咨询研究与售前工作台

> 状态：历史版本；已被 [PRD v0.4](01_PRD_v0.4.md) 替代  
> 日期：2026-08-11  
> 保留原因：记录完整发现过程与早期平台方案；v0.2 保留完整产品愿景与行业研究。  
> 产品类型：人机协作 AI Workflow，不以多 Agent 为首版目标。

## 1. 一句话解释

经纬帮助顾问把“一句模糊问题和少量材料”逐步变成一份有来源、可修改、可继续补料的内部研究初稿。

它不是替顾问一键生成最终报告，而是把顾问原本散落在搜索、网页、PDF、Excel、聊天和 PPT 里的工作连接起来：

```text
理解任务
→ 制定研究计划
→ 搜索或人工补充材料
→ 摘录并核验来源
→ 形成发现、反证和信息缺口
→ 组织报告/PPT 故事线
→ 人工评审、修改和继续研究
```

## 2. 要解决的真实问题

顾问收到任务时，通常不是一套完整数据，而可能只有：

- 领导转述的一句话；
- 一个场地名称或位置；
- 一封客户邮件；
- 几十个零散文件；
- 一个“帮我查一下同行怎么降本增效”的研究要求。

现在的工作方式往往是搜索网页、复制到 Word、人工整理 Excel、在聊天模型里反复粘贴、再写 PPT。由此产生四个问题：

1. 搜过什么、为何保留或排除很难追踪；
2. 网页事实、来源观点、AI 推断和顾问判断容易混在一起；
3. 人补充新材料后，旧结论与大纲无法稳定更新；
4. 普通聊天可以快速写文字，但不能可靠保存一个咨询项目的证据链和返工过程。

## 3. 核心用户与使用边界

### 3.1 第一核心用户

- JLL 等地产、产业、区位和商业策略团队中的 Analyst / Consultant；
- 需要完成售前研究、竞品/案例研究、专题研究和内部汇报初稿的人；
- 当前以有真实材料、能还原关键过程的咨询任务为第一优先。产品能力覆盖项目团队的完整研究流程，不按产品所有者在历史项目中的个人分工设限；历史贡献归属另行记录，不能用“现在可以完成”替代“当时实际完成”。

### 3.2 可扩展用户

- 战略、管理和四大咨询团队中的研究与分析岗位；
- 企业战略、战略运营、商业分析和市场情报团队。

扩展用户共享同一研究证据工作流，但首版不为其单独开发数字化转型、尽调、PMO 等完整模板。

### 3.3 非首版用户

- 需要生产级数据工程、软件开发或系统实施的技术团队；
- 需要自动抓取付费数据库、企业内网或灰色情报的用户；
- 希望 AI 无人审核后直接给客户最终建议的团队；
- 以 Case 面试训练为主要目标的求职者。

## 4. 核心 Job to Be Done

> 当我收到一个定义不清、时间紧、资料不完整的咨询研究任务时，帮助我快速形成可审查的任务理解和研究计划，持续接收公开搜索与人工补充材料，整理出可溯源的证据和发现，并生成一版能交给经理继续讨论的报告或 PPT 故事线；同时让我知道哪些是事实、哪些是假设、还缺什么，以及新材料改变了哪些结论。

## 5. 产品形态判断

### 5.1 MVP 是什么

- 一个持久化的咨询项目空间；
- 一条固定但可暂停、回退和补料的研究 Workflow；
- 一组搜索、文件解析、证据整理、生成和质检能力；
- 多个人工确认点；
- AI 在每个步骤提供候选结果，人决定是否采用。

产品提供三个共享状态的视图：

- 咨询项目画布：按决策逻辑查看问题、诊断、选项与可行性；
- 研究执行看板：按协作逻辑查看工作包、负责人、进度、阻塞与补料；
- 交付故事线：按表达逻辑组织备忘录和 PPT 页面。

三者不是独立系统：研究缺口可生成看板任务，任务产出的证据和发现回填画布，经人工批准的发现再进入交付故事线。

### 5.2 MVP 不是什么

- 不是只有一个输入框的问答机器人；
- 不是把七层框架塞进一个长 Prompt；
- 不是自主完成整个项目的全自动 Agent；
- 不是多个“研究 Agent、分析 Agent、PPT Agent”互相对话的演示；
- 不是咨询公司的 ERP、CRM 或完整项目管理平台。

## 6. MVP 完整闭环

### 6.1 项目起点

用户只需提供以下任一组合即可创建项目：

- 一句话问题；
- 一句话问题 + 地点；
- 一句话问题 + 网页；
- 一句话问题 + PDF/Word/Excel/PPT/图片；
- 已有材料但问题尚不明确。

系统不得因为缺少完整字段而阻止创建项目。

### 6.2 主干流程与并行工作包

以下八个状态描述项目如何从委托推进到内部交付，不代表八个页面必须机械地依次完成。S1—S2建立方向，S3—S5允许多个研究工作包并行、暂停和重开，S6—S8负责综合、交付与返工。

```text
Brief → 决策与假设 → 并行研究工作包 → 证据/发现 → 综合诊断
                                                   ↓
评审与补料 ← 内部交付 ← 可行性与选项 ←─────────────┘
```

地产、产业和园区项目可按需启用：项目本体与运营、区位与市场、产业与需求、客群与产业链、政策、案例与竞品、可行性等工作包。它们属于“纬”，不属于必须逐层通过的“经”。数据分析是贯穿这些工作包的共用方法，不作为所有项目必须单独完成的固定工作包。

#### S1｜任务理解

系统从用户原话中提取：

- 客户或内部委托方可能要做出的决定；
- 研究对象、时间、地区和范围；
- 预期交付物和受众；
- 已知事实、暂定假设和未知项；
- 会改变研究方向的澄清问题。

用户可以修改并确认“任务理解卡”。未确认内容不升级为事实。

#### S2｜研究计划

系统生成可编辑的研究问题、初始假设和搜索计划。每项研究任务至少包含：

- 要回答的问题；
- 为什么会影响客户决策；
- 需要什么证据；
- 建议来源或用户材料；
- 当前状态和优先级。

工作包状态至少包括：未开始、进行中、暂时够用、待补数据、受质疑、已替代。售前阶段允许“暂时够用”，不要求每个模块都完成后才能综合。

#### S3｜公开搜索与材料收件箱

系统支持两种并行输入：

1. 用户发起的公开网页搜索与定向页面读取；
2. 用户上传、粘贴或手工录入的文件、数据和访谈材料。

材料进入收件箱后先保留原文和元数据，不直接变成结论。付费数据库、内网和客户系统中的材料由用户在权限允许时导出上传。

新材料可以在任意时点加入并关联一个或多个工作包。系统应标记它影响的证据、发现、选项和交付段落，只重开受影响部分，而不是要求整个项目从头生成。

搜索结果首先是“候选材料”，不是“已核实事实”。系统必须区分并显示：

- 一手/官方原始来源；
- 可追溯的二手来源；
- 搜索摘要、聚合页或疑似同源转载；
- 用户提供但尚未核验的材料；
- 模型先验或训练记忆形成、无法定位来源的线索。

模型先验只能用于提出搜索词、研究问题和假设。若无法找到可打开、可定位的来源，不得将其写成事实或生成伪造引用；如为推进讨论而保留，必须显示“模型先验/未核验线索”。

#### S4｜证据整理与核验

系统从材料中生成候选证据卡，并记录：

- 原文摘录；
- 来源 URL/文件名及页码、工作表或位置；
- 发布/数据时间和获取时间；
- 地域、单位、统计口径；
- 来源类型与可信度提示；
- 支持或反驳哪个问题/假设；
- 当前状态：待核验、已核验、冲突、过期或排除。

用户可以修改、合并、排除和确认。系统不得把多个转载同一内容的网站当成多个独立来源。

系统不能保证公开网页本身真实，但必须保证来源等级、核验状态和冲突对用户可见。关键事实应尽量回到一手/官方原始来源；找不到时不得静默提升可信度。

#### S5｜发现与分析

系统基于已选证据生成“发现卡”，而不是直接写长报告。每张卡包含：

- Observation：证据显示了什么；
- Interpretation：这可能意味着什么；
- Alternative：还有什么替代解释；
- Implication：对当前决策可能有什么影响；
- Evidence for / against：支持证据和反证；
- Confidence：当前把握；
- Gap：还缺什么信息。

首版支持基础表格整理、对比表和简单计算；复杂财务模型、GIS 和生产级数据分析通过后续模块或外部工具完成，再把结果回填项目。

对于表格和图表，系统还应检查：单位、地域、时间、实际/预测、来源、公式和相邻期间变化是否一致。硬编码数字、缺少来源或增长率与规模数据不闭合时，必须提示而不能直接进入交付物。

#### S6｜研究综合

系统按研究问题把发现整理为：

- 已核实的主要事实；
- 当前可支持的结论；
- 仍待验证的假设；
- 冲突证据和限制；
- 候选方案或下一步研究方向。

信息不足时允许结论是“当前无法判断”，并给出最小补证动作。

综合不是把所有工作包摘要拼接在一起，而是回答：当前的结构性问题是什么、哪些证据支持或反驳、有哪些候选方向、每个方向依赖什么条件。案例仅能证明某种机制在特定条件下出现过，不能单独证明本项目存在需求。

#### S7｜内部交付初稿

MVP 输出一个“内部评审包”：

1. 一页任务理解；
2. 研究范围与方法；
3. 关键发现卡；
4. 来源和证据清单；
5. 信息缺口、风险与替代解释；
6. 建议的报告/PPT storyline；
7. 数据请求、访谈对象或下一步行动。

首版重点是 Markdown/Word 可编辑备忘录和 PPT 页面大纲，不承诺自动生成可直接发给客户的精装 PPT。

#### S8｜评审、补料与继续

用户或经理可以：

- 批准、修改、否决一条发现；
- 上传新材料；
- 重新运行某个研究问题；
- 将结论退回证据不足状态；
- 查看新材料影响的发现和交付段落；
- 保留修改理由和版本记录。

### 6.3 跨步骤规则｜带风险推进（人工覆盖决策门）

在售前、截止时间临近或客户资料缺失时，用户可以强制将项目推进到内部评审或售前沟通，不要求所有工作包完成。系统提供三种处理方式：

1. **按假设推进**：内容进入下一版本，但显著标注假设、缺口和若错误会产生的影响；
2. **从本版排除**：不阻塞交付，相关结论或页面暂不生成；
3. **以区间/情景推进**：不用单点数字，保留多种可能结果及触发条件。

人工覆盖必须生成 OverrideDecision，记录发起人、时间、理由、目标版本、受影响内容和重审条件。它只能改变项目进度，不能把“未核验”“冲突”或“模型先验”改成“已核实事实”。系统可以阻止虚假引用、无来源精确数字和已知错误进入事实状态，但必须允许用户降级表达或排除后继续。

## 7. 两条首批用户路径

### W0｜一句话 + 地点的售前初案

示例输入：

> 华南某镇一处冷链仓大部分已由某仓储会员店使用，剩余约三分之一空间应该做什么？

系统应完成：

```text
识别可能的客户决策
→ 地点和项目公开初查
→ 已知/假设/未知
→ 周边产业、需求、竞品和案例线索
→ 2—4 个候选方向及反证
→ 客户澄清问题和数据请求
→ 售前研究方法与 proposal storyline
```

系统不得虚构面积、租金、能耗、改造成本或客户需求，也不得把单个成功案例当作需求证明。

### W1｜搜索 + 人工材料的专题研究

示例输入：

> 头部券商公司有哪些降本增效方法？

系统应完成：

```text
定义“头部”“降本增效”和研究范围
→ 生成公司/措施/时间/效果字段
→ 搜索公司年报、公告、官方案例和可靠报道
→ 接收用户提供的文件与线索
→ 去重并核验真实来源
→ 区分公司已披露动作、供应商案例和通用推断
→ 按措施、适用条件、证据强度和可迁移性整理
→ 生成带引用的内部研究报告大纲
```

如果公开资料没有披露节省金额，系统只能说明采取了什么措施或记录供应商声称，不得自行推算成公司已实现收益。

## 8. 核心数据对象

| 对象 | 最小作用 |
|---|---|
| Project | 保存问题、范围、位置、模式和项目状态 |
| Brief | 保存用户原话、任务理解和人工确认版本 |
| ResearchQuestion | 保存要回答的问题、优先级和完成状态 |
| WorkPacket | 保存并行研究模块、负责人、状态、输入、输出和停止条件 |
| Hypothesis | 保存暂定判断、验证计划和支持/反证状态 |
| Material | 保存网页、文件、表格、图片或人工输入 |
| Evidence | 保存精确摘录、来源、口径和核验状态 |
| Finding | 保存观察、解释、替代解释、影响和置信度 |
| Option | 保存候选方向、作用机制、适用条件、反证和可行性判断 |
| DeliverableBlock | 保存报告/PPT 中一段内容及其引用 |
| ReviewDecision | 保存批准、修改、否决、理由和时间 |
| OverrideDecision | 保存带风险推进的发起人、理由、目标版本、受影响内容和重审条件 |
| TaskRun | 保存搜索、解析、模型调用、失败和重试记录 |
| ImpactLink | 保存新材料或修改会影响哪些证据、发现、选项和页面 |

最小追溯链：

```text
Material → Evidence → Finding → DeliverableBlock → ReviewDecision
```

## 9. 人机分工与确认门

| 环节 | AI 可以做 | 人必须负责 |
|---|---|---|
| 理解任务 | 提取范围、歧义和澄清问题 | 确认真实目标与对外口径 |
| 研究规划 | 生成问题、假设和来源建议 | 决定优先级与时间投入 |
| 搜索整理 | 搜索、摘录、去重和初步分类 | 判断授权、相关性和是否继续查 |
| 证据核验 | 提示来源等级、冲突和口径缺失 | 确认关键事实是否可用于结论 |
| 分析综合 | 生成发现、反证和替代解释 | 做取舍并承担专业判断 |
| 写作 | 生成结构、摘要和页面大纲 | 审批客户承诺、措辞和最终建议 |

任何步骤都允许人补充材料或直接编辑。人工编辑不应打断工作流，而应形成新版本并触发受影响内容提示。

任何决策门都允许授权用户带风险推进，但事实核验状态与项目进度状态必须分离：页面可以进入售前版本，一条证据仍然可以保持“未核验”。

## 10. 搜索与数据可行性边界

### 10.1 MVP 可以合理实现

- 用户主动发起的公开网络搜索；
- 对允许访问的网页进行正文抽取；
- 读取用户提供的 PDF、Word、Excel、PPT、图片和文本；
- 保存 URL、文件位置、摘录、访问时间和引用；
- 对来源冲突、缺日期、缺口径和转载关系给出提示；
- 搜索失败后保留任务并允许用户补料或重试。

### 10.2 MVP 不能承诺

- 绕过登录、验证码、反爬或付费墙；
- 自动获得 Wind、Capital IQ、企查查高级数据或客户内网权限；
- 仅凭公开网页还原企业内部成本、流程和真实成效；
- 保证所有网页长期可访问；
- 在没有原始数据时生成精确 business case。

因此，经纬的数据策略是“公开搜索 + 用户授权材料 + 人工补充 + 明示缺口”，而不是建设一个无所不知的爬虫平台。

## 11. AI 与 Agent 架构原则

MVP 采用由产品状态机控制的单一 Workflow：

```text
产品决定允许的步骤和工具
→ AI 为当前步骤生成候选输出
→ 用户确认或修改
→ 状态写入项目
→ 继续下一步或回退补证
```

模型不得自行扩大项目范围、发送外部消息、访问未经授权的数据或发布客户材料。

后续只有在真实测试证明某些研究任务需要动态循环，且自动化收益高于错误和审查成本时，才增加受限 Agentic 能力，例如：

- 根据证据缺口选择下一条搜索；
- 识别同源转载后主动寻找原始来源；
- 新证据推翻假设后调整待办；
- 在预算、站点白名单和停止条件内进行多轮研究。

是否拆成多个 Agent 属于实现选择，不能先于工作流价值验证。

首个 Agent 架构对照实验采用P-001 冷链园区竞品租金研究，在相同输入与权限下比较固定 Workflow、单一研究 Agent 和受编排 Multi-Agent。架构保留三种执行策略的兼容性，但首版是否启用多个 Agent 由证据质量、人工复核、延迟、成本和稳定性结果决定。

## 12. 功能优先级

### P0｜首个可测试闭环

- 项目创建与任务理解卡；
- 已知/假设/未知；
- 研究问题与计划；
- 网页/文件/手工材料收件箱；
- 证据卡与精确引用；
- 发现卡与反证；
- 内部评审包和故事线；
- 人工批准、修改、否决；
- 保存、恢复、失败重试和版本记录。

### P1｜验证后增强

- 表格字段映射、去重和基础计算；
- 来源变化和失效链接检查；
- 发现—交付物影响分析；
- Word 导出和 PPT 大纲导出；
- 地产/产业研究字段模板；
- 券商等专题 benchmark 表模板。

### P2｜暂不承诺

- 完整 Excel 模型引擎；
- GIS 深度分析；
- 自动生成精装 PPT；
- 专家访谈机器人；
- PMO 和 benefit tracking；
- 数字化转型、商业尽调等完整模板；
- 多 Agent 协作；
- Case 面试训练。

## 13. 非功能要求

- 用户输入和人工修改在任务失败时不丢失；
- 每个长任务可取消、重试，并显示当前状态；
- 关键结论必须能回到证据原文和来源；
- 网页内容和上传文件均视为不可信输入，不能改变系统指令；
- 不在日志、模型请求预览之外暴露客户敏感信息；
- 远程模型调用前显示将发送的材料范围；
- 搜索结果、AI 输出和人工确认分别记录；
- 所有事实性输出显示来源类型与核验状态；模型先验不得伪装成搜索结果或引用；
- 用户强制推进必须保留风险标记、理由、受影响内容和重审条件；
- 项目可导出，避免被单一模型或服务锁定；
- 在没有模型或搜索失败时，用户仍可手工补料并继续整理。

部署形态暂未最终决定；考虑客户材料的敏感性，产品发现阶段默认优先评估本地优先方案。

## 14. MVP 验收

### 14.1 冷链售前路径

在只提供一句问题和地点、没有客户经营数据时：

1. 能创建项目并生成可编辑任务理解；
2. 不要求先填完完整数据表；
3. 能把事实、假设和未知分开；
4. 能保存至少一轮公开搜索和用户补充材料；
5. 每条关键发现能打开原文引用；
6. 能列出候选方向、反证和验证条件；
7. 能输出内部 proposal storyline 和数据请求；
8. 不出现无来源的精确经营数字或确定性推荐。
9. 即使工作包未完成，授权用户也能选择按假设、排除或情景方式推进，并保留显著风险标记；
10. 模型训练记忆产生但无可核验来源的内容被标记为模型先验，不进入已核实事实。

冷链路径采用三档决策门，而不是要求全部模块逐项验收：

1. **可继续头脑风暴**：任务、初始假设、主要未知项和第一轮案例/市场线索已形成；
2. **可供内部评审**：已有结构性诊断、支持与反证、2—4个候选方向、缺口和下一步补证；
3. **可用于售前沟通**：结论强度与证据匹配，明确数据请求、正式项目方法和客户需要确认的关键决策，不伪装成最终可行性结论。

### 14.2 券商专题研究路径

在提供一句研究问题和若干人工材料后：

1. 能先澄清公司范围、时间和“降本增效”定义；
2. 能合并网页与用户文件并识别重复材料；
3. 能区分公司官方披露、第三方报道和供应商宣传；
4. 能将措施映射到流程、成本/效率目标和适用条件；
5. 未披露的成效不被写成已实现数字；
6. 用户新增材料后，相关发现可更新且保留旧版本；
7. 能输出带来源的报告大纲和仍需核实的问题。

## 15. 验证指标

首轮不预设“节省 80%”等没有基线的数字，记录：

- 从输入问题到第一版可审查任务理解的时间；
- 从开始研究到第一版内部评审包的时间；
- 关键事实的精确引用覆盖情况；
- 无来源数字、错口径和误引的数量；
- 用户接受、修改和否决 AI 候选的比例及原因；
- 新增材料后需要人工重新复制整理的次数；
- 与普通聊天相比，项目重启后恢复上下文和证据的难度；
- 哪一步真正节省时间，哪一步反而增加复核成本。
