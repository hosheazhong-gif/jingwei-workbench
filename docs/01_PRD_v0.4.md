# PRD v0.4｜经纬：咨询研究工作台

> 状态：已被 [PRD v0.5](01_PRD_v0.5.md) 替代；保留审查两栏阶段的完整规格  
> 日期：2026-08-12  
> 替代关系：曾替代 v0.3 作为基线；2026-08-16 起当前基线为 v0.5  
> 当前产品类型：人机协作 AI Workflow  
> 长期愿景：咨询证据到决策工作台

## 1. 本版做出的关键修正

1. 长期仍建设咨询工作台，但首版不同时实现完整画布、团队看板、企业知识库和多 Agent；
2. 首个 MVP 只验证地产与产业咨询中的低信息售前研究闭环；
3. 首要操作者确定为 Analyst / Consultant，经理是首个输出接收者和评审者；
4. “搜索、上传文件、生成带引用报告”不再被视为足够的差异化；
5. 差异化假设收敛为：认识状态分离、补料影响、人工受控推进和证据到交付的连续性；
6. 新增 Claim 作为可独立检查的原子主张；模型先验不再属于证据来源；
7. 可编辑导出和有限影响追踪进入 P0，复杂协作看板降到后续阶段；
8. 增加停止或转向条件，避免只因技术可以实现就持续扩张。

## 2. 长期愿景与当前承诺

### 2.1 长期愿景

> 经纬成为咨询与内部战略团队的证据到决策工作台：把任务、来源、主张、分析、选项、交付和人工决定保存在同一个可追溯项目中，并支持团队协作、重复更新和受限 Agent 执行。

愿景保留三类视图：

- 咨询项目画布：理解问题、证据、发现、选项和风险；
- 研究执行看板：管理任务、负责人、阻塞和补料；
- 交付故事线：将批准内容组织为备忘录、PPT 和工作坊材料。

### 2.2 当前 MVP 承诺

> 帮助一名地产或产业咨询 Analyst，在只有一句任务、一个地点和少量材料时，形成一版可供经理审查、每条关键主张可回到来源、且能在补料后继续更新的内部研究初稿。

首版不承诺管理整个咨询项目，也不承诺替代最终的 PowerPoint、Excel、访谈、专业数据库和经理判断。

### 2.3 架构原则

```text
愿景上保留工作台
→ 对象模型不封死未来扩展
→ 当前只实现最小研究闭环
→ 后续阶段必须由真实验证触发
```

这意味着“平台可兼容”，不意味着现在预先开发平台基础设施。

## 3. 第一性原理下的产品问题

### 3.1 用户不是为了维护框架而工作

顾问真正要完成的是：在时间和信息不足时，交出一份经理能继续判断、修改和对客沟通的材料。用户不会因为一个工具的方法论完整就持续使用；只有当它降低搜索、复制、核对、返工和重新恢复上下文的成本时，产品才成立。

### 3.2 当前真实替代方案

- 网页搜索、企业官网、政府网站和专业数据库；
- ChatGPT、Deep Research、NotebookLM、Notion Research 等通用 AI；
- Word、PowerPoint、Excel、微信/邮件和共享文件夹；
- 经理经验、旧项目模板和同事口头指导。

因此经纬不能仅以“生成更完整报告”为价值，必须证明结构化项目状态的收益大于维护它的成本。

### 3.3 当前核心痛点假设

1. 搜过什么、为何保留或排除难以恢复；
2. 来源原文、事实主张、AI 推断和顾问选择容易混在一起；
3. 新材料出现后，不知道哪些结论和页面需要重新检查；
4. 普通对话能生成文字，但难以稳定承接多轮补料和经理返工；
5. 信息不足时，工具容易阻塞或给出伪确定性结论。

这些仍是待验证的产品假设，不是已证明的市场需求。

## 4. 核心用户、使用时刻与购买边界

### 4.1 首要操作者

- 地产、产业、区位和商业策略团队的 Analyst / Consultant；
- 接收经理的一句话任务并负责 desk research、案例、数据整理和初稿的人；
- 当前原型首先服务产品所有者本人能够还原和测试的真实工作。

### 4.2 下游评审者

- Manager / Project Lead；
- 首版通过可编辑文件、评审链接或批注结果参与，不要求建设完整经理端和组织权限。

### 4.3 当前使用时刻

```text
经理发来一句模糊任务
→ 用户需要在有限时间内形成第一版研究与讨论材料
→ 客户详细资料可能尚未提供
→ 后续仍会补料、改方向或删除部分结论
```

### 4.4 暂不解决的购买问题

首版是产品发现与作品集 MVP，不假设已经获得咨询公司的企业采购。企业版的采购者、合规审批、部署和定价需要在个人闭环成立后单独验证。

## 5. 核心 Job to Be Done

> 当我收到定义不清、时间紧、材料不完整的咨询研究任务时，帮助我快速明确决策问题和最小研究范围，把公开搜索与人工材料整理成可检查的主张和发现，形成能交给经理继续修改的初稿；即使资料不足我也能带风险推进，同时系统不会把未核验内容伪装成事实。

## 6. MVP 最小闭环

### M1｜创建研究任务

输入允许为：

- 一句话；
- 一句话 + 地点；
- 一句话 + 文件/图片/网页；
- 一批材料但问题尚未完全明确。

系统形成一张可编辑 Brief：

- 原始委托；
- 可能需要做出的决定；
- 当前范围和受众；
- 已知、假设和未知；
- 本轮最小交付物。

用户可以直接修改，也可以在未完全确认时继续。

### M2｜形成最小研究计划

系统只生成足以支持本轮交付的研究问题，不自动展开完整咨询框架。每项问题包含：

- 为什么影响当前决策；
- 需要什么材料或证据；
- 可由公开搜索、用户补料、数据处理还是人工判断完成；
- 何时“暂时够用”。

P-001模板可以推荐项目本体、区位市场、产业需求、产业链、政策案例和可行性，但用户不必全部启用。

### M3｜搜索与材料进入统一收件箱

材料类型包括网页、PDF、Word、Excel、PPT、图片、访谈纪要和人工录入。

所有搜索结果先进入 CandidateSource，不自动成为证据。系统保存：

- 原始 URL 或文件；
- 标题、作者/机构、日期和访问时间；
- 文件页码、工作表、单元格或网页位置；
- 来源类型、权限和当前可访问状态；
- 导入时的项目内快照或受控副本、文件哈希与原始路径。

仅保存用户设备或微信缓存中的外部路径不算完成导入。来源状态至少区分 `available`、`path_expired`、`permission_denied` 和 `deleted`；来源失效时保留历史摘录，但触发相关 Claim 和初稿段落重审。

### M4｜形成证据摘录与原子主张

系统从来源中提出 EvidenceExcerpt 和 Claim 候选：

```text
Source
→ 精确摘录或数据位置
→ 一条可以独立检查的 Claim
→ 认识类型和核验状态
```

Claim 认识类型：

- factual_claim：来源声称的事实；
- inference：顾问或 AI 基于事实形成的推断；
- assumption：为推进工作暂时采用的假设；
- judgment：基于目标、经验和权衡作出的选择。

`factual_claim` 表示“某个来源作出了可核验的事实陈述”，不自动表示该陈述已成为现实事实。二次成果页、供应商宣传或新闻转载中的文字可以被准确捕获，但仍要经过原始来源追溯或交叉支持。

模型训练记忆产生但无法定位来源的内容是 ModelSuggestion，不是 Source 或 Evidence。它只能进入搜索计划或假设候选。

### M5｜综合发现与候选方向

系统把已选择的 Claim 组织为 Finding：

- 当前观察；
- 解释与推理链；
- 支持证据；
- 反证和替代解释；
- 对客户决策的影响；
- 仍缺什么。

探索型项目可以进一步生成 Option，但系统不要求所有专题研究都必须产生策略方案。

### M6｜形成内部评审初稿

首版输出：

1. 任务与范围；
2. 关键发现；
3. 候选方向或下一步研究；
4. 主要反证、假设和信息缺口；
5. 来源清单和精确引用；
6. 数据请求、访谈对象或下一动作；
7. 可编辑的 Markdown/Word 内容和 PPT 页面大纲。

首版不追求精装 PPT，但必须避免用户重新复制整理全部文字和来源。

### M7｜人工评审、补料和继续

用户可以：

- 修改、批准、否决 Claim、Finding 和 Option；
- 补充新材料；
- 查看新材料可能影响的 Claim 和 DeliverableBlock；
- 保留旧版本和人工修改；
- 从受影响部分继续，而不是重新生成整个项目。

P0 只实现有限影响追踪：显式记录的 Source—Claim—DeliverableBlock 链发生变化时提示用户，不建设通用知识图谱。

## 7. 人工强制推进

资料缺失、售前或时间紧迫时，授权用户可以跳过研究问题或带风险生成下一版本。

可选处理：

1. 按假设推进；
2. 从本版排除；
3. 按区间或情景表达。

系统自动生成 OverrideDecision，记录理由、目标版本、受影响内容和重审条件。首版应尽量自动填写，不要求用户维护复杂表单。

强制推进只改变项目进度，不改变认识状态：

```text
可以进入售前版本
但相关 Claim 仍然可以是未核验、冲突或假设
```

## 8. 统一对象模型

### 8.1 P0 必需对象

| 对象 | 作用 |
|---|---|
| Project | 保存一次咨询研究任务及当前版本 |
| Brief | 保存原始委托、决策问题、范围、受众和交付要求 |
| ResearchQuestion | 保存本轮要回答的问题及“暂时够用”条件 |
| Source | 保存网页、文件、数据、访谈或用户输入、项目快照、哈希和可访问状态 |
| EvidenceExcerpt | 保存来源中的精确摘录、页码、单元格、网页位置或图片区域 |
| Claim | 保存一条原子主张、认识类型和核验状态 |
| Finding | 保存多条 Claim 综合形成的观察、解释、反证和影响 |
| Option | 保存探索型项目的候选方向、前提、反证和验证动作 |
| DeliverableBlock | 保存初稿中的一段或一页及其 Claim 引用 |
| ReviewDecision | 保存批准、修改、否决和理由 |
| OverrideDecision | 保存带风险推进和重审条件 |

### 8.2 后续对象

| 对象 | 进入条件 |
|---|---|
| ResearchTask / WorkPacket | 验证用户确实需要跨人协作或持续看板后 |
| ImpactLink | P0 使用显式链；复杂跨项目影响分析验证后再扩展 |
| Schedule / Snapshot | 进入重复监测或月报场景后 |
| Interview / Participant / Consent | 进入正式访谈管理后 |
| Model / Scenario | 进入财务、租金或市场模型后 |
| Initiative / Owner / KPI | 只有进入实施和 PMO 产品时，且可能属于独立模块 |

### 8.3 最小追溯链

```text
Source → EvidenceExcerpt → Claim → Finding / Option → DeliverableBlock
                                      ↓
                              Review / OverrideDecision
```

数据计算或模型结果作为可定位的 AnalysisArtifact 支持 Claim，不允许只引用“AI分析结果”。

## 9. 来源、核验与认识状态

### 9.1 Source 类型

- primary_official：政府、公司、原始数据库、合同或客户确认材料；
- secondary_traceable：可定位作者、时间和引用链的二手来源；
- aggregator_or_snippet：搜索摘要、聚合页或疑似同源转载；
- user_provided：用户上传但尚未核验的材料；
- interview：带受访者、时间和适用范围的访谈记录。

ModelSuggestion 不属于 Source 类型。

Source 可访问状态：

- available：项目当前能打开并定位；
- path_expired：外部缓存或临时路径已失效；
- permission_denied：文件仍存在但当前无权读取；
- deleted：已确认源文件被删除。

可访问状态与来源质量是两套属性：一份内部成果页可以 `available`，但仍然只是待追溯的二次来源。

### 9.2 Claim 核验状态

- captured：已捕获，尚未检查上下文；
- source_checked：来源、原文位置和上下文已检查；
- corroborated：有权威原始来源或独立证据支持；
- conflicted：与其他来源冲突；
- stale：可能超出时效；
- unverifiable：当前无法追溯或确认；
- excluded：不进入本轮交付。

系统不承诺判断互联网绝对真伪。“已核实事实”在界面中应谨慎使用，默认更准确地显示“来源已检查”或“已交叉支持”。

### 9.3 禁止行为

- 编造 URL、标题、作者、日期、引文、页码或数字；
- 把搜索摘要当成原文；
- 把同源转载计为多个独立来源；
- 把模型训练记忆伪装成搜索结果；
- 把单个成功案例直接写成项目需求证明；
- 在没有原始数据时生成精确 business case。

## 10. 首版界面与交互

### 10.1 P0 主界面

P-001真实可用性测试后，P0 默认入口收缩为“内部稿 + 来源与主张审查侧栏”：

1. 内部评审初稿作为主工作面；
2. 点击段落可查看“现在能否写、为什么、来自哪里”；
3. 客户来源、核验限制和风险处理显示在相关段落旁；
4. 补料后直接提示受影响的判断与报告段落，并等待局部重审；
5. Brief 与最小研究问题保留为任务边界编辑入口。

Source、EvidenceExcerpt、Claim、Finding/Option 和 DeliverableBlock 仍完整保存在底层。独立研究工作区不作为 P0 默认导航；未来如验证复杂项目确实需要，可作为同一对象的深度视图增加。

聊天是输入和追问方式之一，不是唯一界面。

### 10.2 未来工作深度预设，不属于 P0 双模式开发

以下是 P0 验证成立后的产品形态预留，不代表当前同时开发两种模式。它们只是两种早期工作深度预设，不是对未来咨询课题的封闭分类，也不应成为核心 schema 中固定的二选一字段。

未来的**轻量研究预设**可用于一句话专题研究：

```text
Brief → Sources / Claims → Findings → Draft
```

未来的**结构化项目预设**可在需要时开启：

```text
项目画布 + 简化看板 + Options + 决策门 + 故事线
```

P-001 P0 当前只验证其中最小研究闭环。券商 benchmark、机场专题和轻量研究预设均为后续迁移测试候选，不进入 P0 功能清单。未来工作台可以通过 ProjectTemplate、AnalysisModule、ExecutionStrategy 和不同视图组合出更多工作形态；所有形态必须复用同一核心对象，不能形成互不兼容的数据和代码。

### 10.3 第二阶段愿景原型

现有画布、看板和故事线原型继续保留，用于验证长期工作台的信息架构；它们不全部进入首个可运行版本的完成标准。

## 11. 搜索、数据和模型边界

### 11.1 P0 可以实现

- 用户触发的公开网页搜索和页面读取；
- PDF、Word、Excel、PPT、图片和文本解析；
- 来源与精确位置保存；
- 基础表格整理、单位/时间/地域/实际预测检查；
- 候选 Claim、Finding 和大纲生成；
- 用户批准、修改、否决和带风险推进；
- Markdown/Word 内容与 PPT 大纲导出。

### 11.2 P0 不承诺

- 付费墙、验证码、反爬或企业内网绕过；
- Wind、Capital IQ、AlphaSense 等付费内容自动获得；
- 企业内部成本和需求的自动还原；
- 完整 GIS、财务模型或自动精装 PPT；
- 无人审核后直接向客户发布；
- 企业级多人权限和知识库。

## 12. AI、Workflow 与 Agent

项目状态由确定性编排器管理。具体研究任务可以由人工、固定 Workflow 或受限 Agent 完成，但执行方式不改变对象模型。

P0 固定使用 Workflow，不开发或测试研究 Agent。对象与编排层只保留可替换的 ExecutionStrategy 接缝。只有P-001最小闭环验证成立、且后续真实研究任务证明固定 Workflow 不足时，才在 P1 单独测试单一研究 Agent。

Multi-Agent 是远期内部实现候选，不是首版卖点或当前产品扩展方向。P-001竞品租金对照实验只保留为 P1 以后、满足启动门槛时的独立实验，不在 P0 最小闭环完成后自动启动。

- 组织权限、审计和敏感材料管理；
- 工作文件连接器；
- 重复研究、监测和更新任务；
- 经验证的多个专业 Agent。

### P3｜企业级平台候选

- SSO、组织权限和部署治理；
- 企业知识库和跨项目证据复用；
- 专业数据库与内部系统连接；
- 定时市场情报和复杂数据处理；
- 专业业务线模板生态；
- 在证据支持下考虑 Multi-Agent 编排。

每个阶段是有条件路线图，不是已承诺排期。

### 13.1 扩展性预备：保留接缝，不提前实现未来功能

P0 必须避免把P-001业务词和页面顺序写死在核心层，但不能为了“以后可能用到”先建设完整平台。当前只预留以下稳定接缝：

| 未来扩展 | 当前需要保留的接缝 | P0 不提前实现 |
|---|---|---|
| 新行业/新项目类型 | `ProjectTemplate` / `AnalysisModule` 配置映射到同一核心对象 | 券商、机场、数字化等完整模板 |
| 轻量研究预设 | 同一 Project/Source/Claim/Finding/Deliverable 数据模型的轻量视图 | 第二套独立应用、独立数据库或封闭的二选一模式字段 |
| 个人工作台 | 画布、看板、故事线作为同一对象的不同投影 | 三套重复状态与完整页面 |
| 团队协作 | Review、版本和未来 Role/Task 扩展点 | 组织权限、工时和完整项目管理 |
| 数据与文件能力 | Source、Parser、AnalysisArtifact 的适配器边界 | 一次接入所有数据库、GIS 和模型 |
| Word/PPT/Excel 输出 | DeliverableBlock 到不同导出器的边界 | 精装排版器和完整 Office 替代品 |
| Agent / Multi-Agent | ResearchTask 的执行策略接口 | 当前 Agent 编排、监控和角色体系 |
| 定期情报和月报 | Snapshot/Schedule 后续对象与版本机制 | 定时任务和跨项目监测 |

扩展性不靠空白按钮、万能 `metadata` 字段或提前搭建微服务实现，而靠以下约束：

1. 核心对象不依赖P-001页面名称、固定七层或某个模型；
2. P-001作为模板和样本存在，不作为核心数据库结构；
3. 内部 ID 稳定但默认对用户隐藏，界面使用自然语言名称；
4. 对象 schema 带版本号，后续修改通过迁移而不是直接覆盖旧数据；
5. 人工修改、来源快照和评审记录不能因重新生成而丢失；
6. 新视图只能读取同一事实底盘，不另建一套结论；
7. 新功能先通过真实第二场景验证，再进入核心或模板。

技术设计阶段必须用一个最小“扩展演练”检查架构：在不修改核心对象的前提下，能否新增一个假的第二模板和一个新的导出器。该演练只验证接缝，不实现券商或机场功能。

## 14. 扩展准入规则

一个方向只有在以下条件大体成立时，才直接并入经纬：

1. 主要操作者仍是同类顾问或战略分析人员；
2. 仍然遵循 Source—Claim—Finding—Option—Deliverable 的闭环；
3. 能复用多数对象和人工评审逻辑；
4. 权限、风险和交付责任没有根本变化；
5. 它强化当前闭环，而不是只增加一个新的报告模板。

### 14.1 可作为模板并入

- 地产、园区和产业策略；
- 政策、案例和竞品研究；
- 券商或企业降本增效 benchmark；
- 市场进入和增长战略的研究/选项阶段；
- 企业市场情报和产品研究。

### 14.2 可作为底层能力并入

- Excel 数据处理和 QA；
- 访谈材料与观点归属；
- Word/PPT 输出；
- 定期来源更新和月报模式；
- 受限研究 Agent。

### 14.3 仅部分复用或作为专业模块

- 数字化转型：研究、现状诊断、用例和路线图可复用，技术实施/UAT 不直接并入；
- 商业尽调：研究底座可复用，完整 CDD 的安全、模型和责任要求需要专业版本；
- 定价和客户分析：需要交易数据与专门模型，不能只换模板；
- PMO 和 benefit tracking：可能成为独立实施模块；
- Case 面试训练：保持独立产品。

## 15. 首轮验证设计

### 15.1 唯一主案例

首轮只用P-001 冷链园区完成端到端验证。券商降本增效保留为第二个迁移测试，不与P-001同时定义首版功能。

### 15.2 对照方式

同一输入分别采用：

1. 原人工流程；
2. 普通 AI / Deep Research；
3. 经纬最小流程。

比较：

- 到第一版可审查初稿的时间；
- 关键 Claim 的精确来源覆盖；
- 无来源数字、错口径和错误引用；
- 用户修改、排除和补证次数；
- 新材料加入后的重复复制和返工；
- 中断后恢复项目状态的难度；
- 输出进入 Word/PPT 后需要重做的程度；
- 用户是否愿意在第二个真实任务继续使用。

首轮先建立基线，不预设无依据的节省百分比。

## 16. MVP 完成标准

P-001案例能够完成：

1. 从一句任务和现有材料创建 Brief；
2. 只选择本轮必要研究问题；
3. 公开网页和用户材料进入统一 Source 列表，并保存项目快照、哈希和可访问状态；
4. 关键事实拆成可打开精确位置的 Claim，图片类来源支持区域定位；
5. 推断、假设、顾问判断和 ModelSuggestion 不与事实混写；
6. 形成带反证和缺口的 Finding；
7. 形成内部评审初稿和可编辑导出；
8. 新增材料、替换文件或来源失效后提示受影响的 Claim 和初稿段落；
9. 用户可带风险推进而不升级认识状态；
10. 保存人工修改、否决和版本；
11. 整个流程不要求用户重复维护多套状态。

## 17. 停止或转向条件

出现以下情况，应停止扩平台并重新收窄：

- 用户维护 Claim、状态和引用的时间大于减少的返工；
- 用户只使用一次生成，随后立即回到聊天和 PPT，不再回到项目；
- 经理不关心证据状态、反证和补料影响；
- 经纬相对普通 AI 没有减少关键事实错误或上下文恢复成本；
- 可编辑导出仍要求用户重新复制和排版大部分内容；
- 真正有价值的只有文件问答或报告生成。

可能的转向：

- 收缩为咨询研究证据整理器；
- 做成 Word/PPT/Notion 的插件或导出层；
- 只保留地产产业售前模板；
- 将复杂画布和团队功能停止在愿景原型。

## 18. 隐私与部署边界

产品发现阶段只使用公开、脱敏或用户明确允许的材料。远程模型调用前必须显示将发送的材料范围。

企业级本地部署、SSO、组织权限和数据驻留是后续独立验证项，不能用“未来可以解决”掩盖当前无法处理真实客户敏感材料的事实。
